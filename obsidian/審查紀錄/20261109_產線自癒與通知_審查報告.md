## 結論先行

**這次的改動方向錯了一層，而且錯得可以指出具體位置。**

所有三次事故的共同症狀是「檔案寫好了，`git` 卻看不到它」。本次改動把它當成
**Google Drive 寫入延遲**，於是在延遲之上疊「自我修復」與「60 秒重試」。

Git 官方文件說 fsmonitor 的作用正是讓 `git status`「**avoid scanning the disk**」，

也就是說：**整個堆疊裡唯一一個被官方明文拒絕保證、而且其設計目的就是「不去看磁碟」的元件，

### 🔴-1 根因找錯層：`core.fsmonitor` + `core.untrackedCache` 開在 Google Drive 的工作區上

**實測（2026-11-09，本機 KEN-PC，git 2.55.0.windows.3）**

```
$ git config --list --show-origin | grep -i fsmonitor
file:.git/config        core.fsmonitor=true

$ git config --get core.untrackedCache
true

$ git fsmonitor--daemon status
fsmonitor-daemon is watching 'G:/我的雲端硬碟/ai agent/Queen-of-Auctions'

$ git config --get fsmonitor.allowRemote
(unset)
```

`.git/index` 同時帶有 `FSMN` 與 `UNTR` 兩個 extension（已用 Python 讀 index 標頭確認），
表示 `git status` **正在採用**常駐程式回報的變更清單與快取的未追蹤清單，而不是掃磁碟。

**官方文件原文**（git-fsmonitor--daemon，REMARKS 與 CAVEATS）：

> Performance of commands such as `git status` can be increased if they just ask for a summary
> of changes to the working directory and **can avoid scanning the disk**.

> By default, the fsmonitor daemon refuses to work with network-mounted repositories; this may be
> overridden by setting `fsmonitor.allowRemote` to `true`. Note, however, that the fsmonitor daemon
> is **not guaranteed to work correctly** with all network-mounted repositories, so such use is
> considered **experimental**.

> ... the fsmonitor daemon is **not guaranteed to work** with these filesystems and such use is
> considered **experimental**.

- 來源：<https://git-scm.com/docs/git-fsmonitor--daemon>（查證日 2026-11-09）
- 來源：<https://git-scm.com/docs/git-config>（`core.checkStat`：「many fields in the stat structure are checked to detect if a file has been modified since Git looked at it」，查證日 2026-11-09）

**關鍵細節**：`fsmonitor.allowRemote` 並未設定，常駐程式卻照開——
說明 git **沒有把這個 Google Drive 掛載點判定為 network-mounted**，
所以官方設計的那道「預設拒絕」保護根本沒有啟動。這是最壞的組合：
官方不保證正確，而官方的保護機制又剛好擋不住這種掛載形式。

**這個機制同時解釋三次事故的全部特徵**（下節 🔴-5 有 a45264d 的硬證據）：

| 觀察到的現象 | fsmonitor 假說下的解釋 |
|---|---|
| 檔案寫好、`git add -A` 卻沒收到 | 常駐程式沒回報該路徑 → status/add 跳過不掃磁碟 |
| purge 自己的核對「通過」 | 核對用的也是 `git status`，問的是同一個快取 |
| 60 秒重試每圈結果都一樣 | 快取沒有因為時間經過而失效 |
| 兩天後的排程才看到它變髒 | 常駐程式重啟（登出／重開機）→ FSMN token 失效 → git 回退成全掃 → 差異浮現 |

**建議修正（立刻可做，兩行，可回復）**


### 🔴-2 `git add -A` 與白名單判斷範圍不一致（指示第 3 點：**成立**）

**已實際讀程式碼確認，不是理論疑慮。** `run_pipeline.ps1` L99–L126：

```powershell
$dirty = & git -C $SITE_REPO status --porcelain   # ← 快照在這裡拍下
...
foreach ($ln in $dirty) { ... }                   # ← 只檢查快照裡的這幾筆
if ($unsafe.Count -gt 0) { Die ... 3 }
& git -C $SITE_REPO add -A                        # ← 收整個工作區，不只快照那幾筆
```

**官方文件原文**（git-add，`-A`／`--all`）：

> If no _<pathspec>_ is given when `-A` option is used, **all files in the entire working tree are updated**
> (old versions of Git used to limit the update to the current directory and its subdirectories).

- 來源：<https://git-scm.com/docs/git-add>（查證日 2026-11-09）

**實測佐證**（隔離的臨時 repo，git 2.55.0.windows.3，2026-11-09）：
在同時存在 ` M 104woo.html`、` M w123/index.html`、` D keep.txt`、`?? w999/` 的狀態下，
`git add -An`（dry-run）輸出為

```
add '104woo.html'
remove 'keep.txt'
add 'w123/index.html'
add 'w999/index.html'      ← 白名單判定為 unsafe 的孤兒資料夾，add -A 照收
```

所以**只要在 `git status` 與 `git add -A` 之間出現任何新變動，它就會被收進這個 commit，
而且 commit 訊息還會聲稱「全部是產線產物」。** 而這個時間窗正是 🔴-1 描述的場景最容易發生的地方：
上一輪寫入的檔案延遲浮現。commit 訊息裡寫的「未追蹤的新資料夾……仍然會讓產線停下來等人處理」
是**假的保證**——它只對快照時刻成立。

**建議修正**：收集通過白名單的路徑，只 add／commit 那些路徑。
git 官方文件確認 `git commit` 可用尾隨 pathspec 限制範圍：

> When _<pathspec>_ is given on the command line, commit the contents of the files that match the
> pathspec **without recording the changes already added to the index**.

- 來源：<https://git-scm.com/docs/git-commit>（查證日 2026-11-09）

```powershell
$own    = '^(104woo\.html|w\d+/index\.html)$'
$unsafe = @()
$safe   = @()
foreach ($ln in $dirty) {
  $code = $ln.Substring(0, 2)
  $path = $ln.Substring(3)
  if ($code -ceq ' M' -and $path -cmatch $own) { $safe += $path } else { $unsafe += $ln }
}
if ($unsafe.Count -gt 0) { ... Die ... 3 }

# 只動白名單內的路徑；-- 之後是 pathspec，add -u 不會引入新的未追蹤檔
& git -C $SITE_REPO add -u -- @safe
NeedOk 'git add（自我修復）'
& git -C $SITE_REPO commit -q -F $rmsg -- @safe
NeedOk 'git commit（自我修復）'

# 收拾完要再確認一次工作區真的乾淨了，否則是另一種假成功
$still = & git -C $SITE_REPO status --porcelain
if ($still) { Die '自動收拾後工作區仍不乾淨' 3 }
```

> `-u`（`--update`）官方定義：「Update the index just where it already has an entry matching
> _<pathspec>_ ... but **adds no new files**」。這正是這裡要的語意——只收已追蹤檔案的修改。
> 來源同上 git-add，查證日 2026-11-09。

`purge_expired.py` L157–L180：


**第一個 `commit` 失敗（例如 `stage_all()` 當下一個檔案都還看不到 → nothing to commit）時，
程式只印一行「（無變更或 commit 失敗）」就繼續，接著迴圈裡的 `--amend` 會改寫 `HEAD`，
而此時的 `HEAD` 是上一個不相干的 commit。**

**實測重現（隔離 repo，2026-11-09）**

```
HEAD before = deec2a1 feat(items): 上架 5 筆（假設已 push）
--- purge 第一次 commit（還沒 stage 到任何東西）:
On branch master
Changes not staged for commit:
--- 之後檔案可見了，迴圈裡執行 commit --amend --no-edit:
HEAD after amend = ab12e61 feat(items): 上架 5 筆（假設已 push）
 104woo.html     | 2 +-
 w123/index.html | 2 +-
 3 files changed
```

SHA 從 `deec2a1` 變成 `ab12e61`，清除的內容被塞進「上架 5 筆」這個訊息底下。
之後 `head_count()` 會通過（筆數正確）、工作區乾淨 → **照樣執行 `git push`**。
而 `run_pipeline.ps1` 第 10 步早就把上一個 commit 推上去了，於是：

push 被拒（non-fast-forward）→ 本地與 origin 分叉 → **下一次排程的
`git pull --ff-only origin main` 失敗 → Die 2 → 產線從此卡死，而且卡的理由跟原因毫無關聯。**

**官方文件原文**（git-commit，`--amend`）：

> Replace the tip of the current branch by creating a new commit. ...
> You should understand the implications of rewriting history if you amend a commit that has already been published.

- 來源：<https://git-scm.com/docs/git-commit>（查證日 2026-11-09）

**建議修正**：amend 前先確認 `HEAD` 真的是自己剛建立的那個 commit。

```python

r = git("commit", "-m", f"{PURGE_SUBJECT}（{len(purge_codes)} 筆：...）\n\n...")
if r.returncode != 0:
    print("❌ 第一個 commit 沒有成功——不進入 amend 迴圈，避免改寫上一個 commit。")
    print("   請人工確認工作區後重跑。")
    sys.exit(2)

base_sha = git("rev-parse", "HEAD").stdout.strip()

while True:
    stage_all()
    if git('diff', '--cached', '--quiet').returncode != 0:
        if git("rev-parse", "HEAD").stdout.strip() != base_sha:
            print("❌ HEAD 已不是本次的 commit，停止 amend。"); sys.exit(2)
        if not git("log", "-1", "--format=%s").stdout.startswith(PURGE_SUBJECT):
            print("❌ HEAD 主旨不是本次清除，停止 amend。"); sys.exit(2)
        git('commit', '--amend', '--no-edit')
        base_sha = git("rev-parse", "HEAD").stdout.strip()
```

### 🔴-6 自我修復的 commit 沒有保證推送；`-DryRun` 也會 commit

**建議修正**


**官方政策原文要點**：
- 「an absolute **maximum of 1 request per second**」
- 「Scripts running longer than a day, **or run at regular intervals**, are limited to **4 requests per minute**」
- 「Periodic app requests are **considered bulk geocoding** and are **strongly discouraged**」
- 「Results **must be cached** on your side」；重複送同一查詢的客戶端可能被封鎖
- 「you might have your access withdrawn」

這支腳本由工作排程器**每週固定跑兩次**（實測 trigger 為 `MSFT_TaskWeeklyTrigger`，

因此適用的是 **4 req/min**，不是 1 req/s。

另外兩個加重因素：
1. `_geocode_cache` 只存在記憶體，**每次執行都重新查一遍同樣的地址**——
   正是政策點名「repeatedly send the same query may be blocked」的行為。
2. `run_pipeline.ps1` 先跑 `--dry-run` 再跑實跑，而 `geocode_address`／`gen_poi`
   在 dry-run 時**照打外部 API**（L597–L599、L619 都不在 `if not DRY` 裡）。
   所以每次排程對 Nominatim／Overpass 的請求量是**兩倍**。
   順帶指出：`.PARAMETER DryRun` 寫「不寫任何檔案」是對的，但很容易被誤讀成「不連外」。

**建議**

```python

# 2) 快取落地，跨次執行不重複查
CACHE = REPO / "output" / "geocode-cache.json"

    try:    return json.loads(CACHE.read_text(encoding="utf-8"))
    except Exception: return {}

    if DRY: return (None, None)
    ...
def gen_poi(lat, lng):
    if DRY or lat is None: return ("…請洽現場。", "…請洽現場。", "…請洽現場。", [])
```

⚠️ 第 3 點會讓 dry-run 與實跑的統計口徑不同；`run_pipeline.ps1` 第 3 步有

## ✅ 查證後沒問題

### ✅-1 `Substring(0,2)` / `Substring(3)` 的解析是正確的（指示第 1 點前半：成立）

**官方文件原文**（git-status，Short Format 與 Porcelain Format Version 1）：

> `<xy> <path>` / `<xy> <orig-path> -> <path>` ...
> The fields (including the `->`) are separated from each other by a single space.
> ... The user's `status.relativePaths` configuration is not respected;
> **paths shown will always be relative to the repository root.**

- 來源：<https://git-scm.com/docs/git-status>（查證日 2026-11-09）

兩個字元狀態碼 + 一個空白 + 路徑 → 路徑從索引 3 開始，`Substring(3)` 正確。
porcelain v1 的路徑**一律相對於 repo 根目錄**，所以白名單用 `^104woo\.html$`、
`^w\d+/index\.html$` 這種根相對寫法是對的，且不受 `git -C` 之外的 cwd 影響。

**實測確認**（2026-11-09，隔離 repo）：

```
[ M 104woo.html]       → code=[ M] path=[104woo.html]
[ D keep.txt]          → code=[ D] path=[keep.txt]
[ M w123/index.html]   → code=[ M] path=[w123/index.html]
[?? w999/]             → code=[??] path=[w999/]
```

### ✅-2 rename、含空白、非 ASCII 路徑都被擋在白名單外（fail-safe）

指示第 1 點擔心 `R  a -> b` 與引號路徑讓 `Substring(3)` 出錯。**實際上不會造成錯誤收拾**，
因為狀態碼檢查先把它們擋掉了：

```
[R  104woo.html -> renamed.html] → code=[R ] → 不是 ' M' → unsafe → Die 3
```

非 ASCII 路徑確實會被加引號並以八進位轉義，**官方文件原文**：

> Commands that output paths (e.g. _ls-files_, _diff_), will quote "unusual" characters in the pathname
> by enclosing the pathname in double-quotes and escaping those characters with backslashes ...
> or bytes with values larger than 0x80 (e.g. octal `\302\265` for "micro" in UTF-8).
> ... **The default value is true.**

- 來源：<https://git-scm.com/docs/git-config>（`core.quotePath`，查證日 2026-11-09）

**實測**：


程式的 `.Trim('"')` 只去引號、不解轉義，結果是 `\344\270\255…`，
不可能匹配 `^(104woo\.html|w\d+/index\.html)$` → unsafe → Die 3。**保守停下來，正確。**

### ✅-3 未追蹤的 `?? wNNN/` 不自動收拾（指示第 4 點：成立）

## 請特別挑戰的三點：逐點回覆

### 第 1 點：白名單會不會太寬或太窄

**兩邊都有問題，而且「太寬」已經造成實害。**

- **太寬**：`wNNN/index.html` 與 `104woo.html` 被修改時，`git status` **無法區分是產線寫的還是人改的**。
  `7e5713e` 就是鐵證——手插的 `<!-- 自我修復測試 -->` 被自動 commit，還附上一段關於
  Google Drive 的因果敘述。**`104woo.html` 尤其危險**：它是全站資料的單一真理源，
  一個改到一半的 BASE_ITEMS 被自動 commit 並推上線，後果比任何單一物件頁都大。
  → 修法見 🔴-3：用產線自己的寫檔紀錄當依據，不要用路徑猜來源。
- **太窄**：`card.jpg`、`hero.jpg`、`voice.mp3` 的修改與**所有刪除**（` D`）都不在白名單內。
  而 2026-10-13 事故（122 筆清除）的型態正是刪除；`publish_new.py` 就地更新也會主動刪
  `voice.mp3`／`card.jpg`／`hero.jpg`。
  → 這些都會 `Die 3`，fail-safe 但不會自己復原。修法見 🟡-1。

### 第 2 點：`git add -A` 的矛盾

**成立，而且不只是理論。** 詳見 🔴-2：
官方文件確認無 pathspec 的 `-A` 收整個工作區；實測 `git add -An` 在白名單判定為 unsafe 的
`?? w999/` 上照樣輸出 `add 'w999/index.html'`。
判斷用的是 `git status` 的**快照**，執行用的是 `add -A` 的**當下**，兩者之間的任何新變動
都會被收進一個聲稱「全部是產線產物」的 commit。
**你對這個地方的不放心是對的，修法是用 `git add -u -- <白名單路徑>` + `git commit ... -- <白名單路徑>`。**

### 第 3 點：是否整個方向都錯了

**方向錯了，但不是你想的那個原因，所以代價比你預期的低很多。**

你的假設是「問題在 Google Drive，所以要搬 repo」。
但本次審查找到的是：**這台機器的 repo 上開著 `core.fsmonitor=true` 與
`core.untrackedCache=true`，常駐程式正在監看 G: 上的工作區**（🔴-1）。
這是整個堆疊裡唯一一個**設計目的就是「不去掃磁碟」**、而且**官方明文拒絕保證**的元件。
Git 自己的「網路掛載一律拒絕」保護對這個 Drive 掛載形式沒有生效（`fsmonitor.allowRemote` 未設卻照開）。

**所以先做兩行 config，再談搬遷。**

| 方案 | 代價 | 風險 | 可回復性 |
|---|---|---|---|
| **A. 關掉 fsmonitor / untrackedCache**（建議先做） | 兩行指令 + `git status` 慢幾秒 | 幾乎為零 | 立刻可回復 |
| **B. `git gc --prune=now`** 清掉孤兒 idx（🟡-10） | 一次數分鐘 | 低 | 不需回復 |
| **C. 搬 repo 到本機碟，只讓產出同步到 Drive** | 見下 | 中 | 可回復（舊目錄留著） |

**方案 A 若做滿 6 次排程（約 3 週）仍再出現 exit 3 或漏檔，才值得付 C 的代價。**
理由：如果 A 沒解決，就證實問題真的在檔案系統層，那時搬遷有明確依據；
如果 A 解決了，C 就是在修一個不存在的問題——而那正是你自己在 §3.1 寫的
「推導不能取代查證」。

**方案 C 的實際代價（實測數據，2026-11-09）**

  就把「一個會延遲的檔案系統」換成「一個會延遲的複製步驟」——
