## 2. 挑戰審查指示本身的錯誤（Adversarial Challenge）

### 2.1 駁回指示主張 7：AppData 目錄並非無法執行，而是配置引號錯誤

* **審查指示原文**：  
  *「放在 `%LOCALAPPDATA%` 的腳本工作排程器執行不了。2026-09-19 實測：腳本在 AppData 回 `0x8007010B` 或 `0xFFFD0000`，搬到 `C:\Users\ken\Scripts` 後正常。確認成因（當時 Defender 服務未執行、AppLocker 無規則）」*
* **查證與事實駁斥**：  
  1. **`0x8007010B` 的真實意義**：  
     微軟官方 Win32 錯誤碼定義：`0x8007010B` 為 `HRESULT_FROM_WIN32(ERROR_DIRECTORY)`（錯誤代碼 267），官方描述為 **"The directory name is invalid."**。在 Windows 工作排程器中，此錯誤 99% 發生的原因為：在動作設定的 **「開始於 (選擇性) / Start in (optional)」** 欄位中**包含了雙引號**（例如填入 `"C:\Users\ken\AppData\..."`）。微軟 Task Scheduler 規範明確指出，該欄位由底層 API 直接讀取，禁止任何外加引號。
  2. **`0xFFFD0000` 的真實意義**：  
     轉換為帶正負號 32 位元整數為 **`-196608`**。這是 PowerShell CLI（`powershell.exe`）專屬的無效引數/檔案不存在退出碼。通常出現在排程器將引數整個以引號包覆、或 `-File` 指向的路徑引號不配對時。
  3. **結論**：  
     Windows 10/11 在預設情況下，完全允許工作排程器在互動或非互動權限下執行使用者 `%LOCALAPPDATA%` 下的腳本。當初搬到 `C:\Users\ken\Scripts` 能跑，是因為重新手動建立排程動作時去除了錯誤引號。審查指示將其歸結為「AppData 執行不了」屬於倒果為因（Post hoc fallacy）的錯誤推論。
* **官方來源**：  
  - Microsoft Learn: [System Error Codes (0-499) - ERROR_DIRECTORY (267)](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)（查證日期：2026-11-09）
  - Microsoft Learn: [about_PowerShell_exe - Exit Codes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe)（查證日期：2026-11-09）

### 2.2 駁回指示主張 6 的假想風險：purge 不會「漏」，但會「鎖死」

* **審查指示原文**：  
  *「以時間為界的重試在延遲無上限時是否仍可能漏。此機制至今未被實戰驗證」*
* **查證與邏輯反駁**：  
  閱讀 `purge_expired.py` 第 182–197 行源碼：
  ```python
  in_head = head_count()
  left = git("status", "--porcelain").stdout.strip()
  if in_head != len(keep) or left:
      print(f"❌ commit 內容與預期不符：HEAD 版 BASE_ITEMS {in_head} 筆、應為 {len(keep)} 筆")
      print("   ⚠ 不推送，請人工確認後再處理。")
      sys.exit(2)
  ...
  if args.push:
      p = git("push", "origin", "main")
  ```
  1. **不會漏推**：當 Google Drive 延遲超過 60 秒，工作區 `git status --porcelain` 仍有殘留（`left != ""`），或者 HEAD 提交筆數與 `keep` 不一致時，腳本**無條件執行 `sys.exit(2)`**，根本不會執行 `git push`。因此線上 GitHub Pages 絕不可能收到不一致的半成品。指示擔憂的「漏推」在程式邏輯上已被嚴格防死。
  2. **真實風險是指示未點出的「工作區污損連鎖死鎖」**：  
     `purge_expired.py` 在執行 commit 之前就已經呼叫了 `shutil.rmtree` 刪除了資料夾。一旦 60 秒超時退出，本地檔案系統處於「資料夾已被實體刪除、但 git 索引未完全提交」的狀態。工作區狀態會出現大量的 ` D wNNN/index.html`。  
     此時，`run_pipeline.ps1` 的自癒機制只認 ` M`，面對 ` D` 會直接判定為 `$unsafe`，導致往後的每一次排程全部在第 0 步噴出 Exit 3。**自癒系統在遇到逾時的 purge 時完全失去修復能力，形成永久死鎖。**

## 3. 特別挑戰之三大核心議題深度審查

### 3.1 核心挑戰一：在 Google Drive 上跑 Git 是否根本方向錯誤？

> **結論：是的，整個修復方向完全是「治標不治本」的過度工程。唯一徹底的解決方案是將 Git Repo 搬回本機 SSD。**

#### 1. 第一性原理剖析
Git 是針對 POSIX / 本機 NTFS 檔案系統設計的分散式版本控制系統。其可靠性高度依賴以下底層語意：
- `stat()` 呼叫取得微秒級檔案修改時間（mtime）與大小，以快速判斷檔案是否 dirty。
- 原子性重命名（Atomic `rename`）維護 `.git/index` 與引用指標（Refs）。
- 嚴格的檔案鎖定（Lockfiles，如 `index.lock`）。

Google Drive for Desktop 是一個**使用者態虛擬檔案系統（Cloud-based Virtual File System）**，其運作機制是攔截 I/O，透過網路快取池非同步上傳下載。這必然引入：
1. **元數據通知延遲**：本地行程剛寫入檔案，虛擬檔案系統驅動程式尚未刷新快取目錄或通知作業系統，導致 Git 掃描時讀到舊的目錄快照。
2. **檔案鎖衝突**：Drive 同步行程嘗試上傳頻繁變動的 `.git` 內部檔案（如 `index`、`logs/HEAD`），導致 Git 在執行提交時偶發性拋出 `Permission denied` 或 `Unable to create '.git/index.lock'`。

#### 2. 檢視使用者既有規則的衝突
使用者全域規則（`CLAUDE.md`）第 5 條明確規定：
> **② GitHub: remote origin 是跨電腦的唯一通道——沒推上去，另一台就拿不到。**

既然跨電腦同步的權威真理源是 GitHub，那麼**將 Git 工作區放在 Google Drive 雲端同步資料夾內，完全是重複且有害的設計**。

#### 3. 搬遷代價與風險評估
* **搬遷目標**：移至 `C:\Users\ken\Projects\Queen-of-Auctions`（或 `C:\repos\`）。
* **修改成本（極低）**：
  1. `launch_pipeline.ps1` 中的 `$PipelineScript` 預設路徑。
  2. `G:\我的雲端硬碟\ai agent\法拍 104\publish_new.py` 第 37 行：`REPO = Path(r"C:\Users\ken\Projects\Queen-of-Auctions")`。
  3. Windows 工作排程器引數路徑更新。
* **搬遷收益（極高）**：
  - 徹底消滅檔案可見性延遲。
  - `run_pipeline.ps1` 甚至不再需要第 0 步自癒。
  - `purge_expired.py` 不需要 60 秒的輪詢重試迴圈。
  - `launch_pipeline.ps1` 不需要花 20 分鐘等待 G: 掛載。
  - 產線執行時間可縮短數分鐘，且穩定度提升至 100%。

### 3.2 核心挑戰二：白名單會不會太寬或太窄？

`run_pipeline.ps1` 的白名單正則式：
```powershell
$own = '^(104woo\.html|w\d+/index\.html)$'
```

#### 1. 致命缺陷：白名單太窄（造成合法產線更新被阻擋）
在流標重新排拍（就地更新）或部分腳本中途失敗的場景下，產線產物**絕不僅有 HTML 檔案**：
- **`wNNN/card.jpg` 與 `wNNN/hero.jpg`**：由 `burn_price.ps1` 產生。當物件價格異動就地更新時，舊的燒價圖會被重新生成替換。若先前的批次在 Step 5 執行後中斷，或因 Drive 延遲未被 stage，工作區會出現 ` M w123/card.jpg`。
- **`wNNN/voice.mp3`**：由 `local_voice_batch.py` 產生。更新物件若重新產生語音，狀態為 ` M w123/voice.mp3`。
- **後果**：當上述合法產線檔案變更時，因為不符合 `$own`，全部被丟進 `$unsafe`，產線直接拋出 `Die ... 3` 停擺！原本要自癒，反而被過窄的白名單卡死。

#### 2. 致命缺陷：白名單太寬（無意間吃掉人工修改）
- **情境**：工程師或管理者手動調整某個物件頁 `w500/index.html`（例如排版微調、修補某個特定標籤），尚未測試完畢且不打算立即上架。
- **後果**：每週三、六上午 09:07 排程一到，自癒程式碼看到 ` M w500/index.html` 符合 `$own`，**在未經任何語法、內容校驗的情況下，自動執行 commit 並 push 到正式生產環境！** 尚未完成的人工改動直接被當作「產線殘留」推上線。

### 3.3 核心挑戰三：`git add -A` 的自相矛盾與 TOCTOU 競態

* **程式碼位置**：`run_pipeline.ps1` 第 112–126 行
* **矛盾本質**：
  ```powershell
  # 階段 1：逐一檢查 $dirty，宣稱只放行白名單
  foreach ($ln in $dirty) {
      if ($code -ne ' M' -or $path -notmatch $own) { $unsafe += $ln }
  }
  if ($unsafe.Count -gt 0) { Die ... 3 }

  # 階段 2：宣稱「全部是產線產物，自動收拾」，卻執行全工作區吸納！
  & git -C $SITE_REPO add -A
  ```
* **嚴重風險論證**：
  1. **TOCTOU 競態（Time-of-Check to Time-of-Use）**：  
     整個系統發生的所有延遲，正是因為 Google Drive 延遲顯示檔案。假設在執行第 99 行 `git status` 時，某個未追蹤的孤兒資料夾 `w999/` 尚未被虛擬檔案系統索引，但在第 125 行執行 `git add -A` 的當下剛好完成同步，`git add -A` 會**毫無防備地將 `w999/` 全部 stage 進暫存區**！
  2. **違背最小權限原則**：  
     既然在第 1 階段已經驗證過 `$dirty` 中的檔案清單都是合法的，為什麼不使用 `git add -- $safeFiles` 精確加入特定檔案，而要使用具有全局破壞性的 `git add -A`？
  3. **判定**：🔴 **此處是嚴重的邏輯漏洞，必須立即修正。**

## 4. 待驗證技術主張（#1 ～ #8）逐項查證

### 主張 1：`git status --porcelain` 格式解析是否正確？

* **主張內容**：第 1、2 字元為狀態碼，第 4 字元起為路徑。
* **判定**：✅ **沒問題（符合官方標準）**
* **權威查證**：  
  根據 Git 官方文件 `git-status` 的 "Porcelain Format Version 1"：
  - 輸出格式固定為 `XY PATH`。
  - `X` 代表暫存區相對於 HEAD 的狀態（字元索引 0）。
  - `Y` 代表工作區相對於暫存區的狀態（字元索引 1）。
  - 第 3 個字元（字元索引 2）固定為 ASCII 空格 `' '`。
  - 第 4 個字元（字元索引 3 起）為相對儲存庫根目錄的路徑。
  - PowerShell 中 `$ln.Substring(0, 2)` 正好取得 `XY`，`$ln.Substring(3)` 正好取得第 4 字元起的字串。
  - **邊界情況處理**：
    - 若路徑包含雙引號（Git 在路徑含空白或非 ASCII 字元時依 `core.quotePath` 預設加雙引號），程式碼第 115 行使用了 `.Trim().Trim('"')`，能正確剝離最外層引號。
    - 若發生檔案重命名（`R  old -> new`），其狀態碼為 `R ` 或 ` R`，在第 116 行 `$code -ne ' M'` 就會被攔截進 `$unsafe`，不會誤判。
* **官方來源**：  
  - Git SCM: [git-status documentation - Porcelain Format Version 1](https://git-scm.com/docs/git-status#_porcelain_format_version_1)（查證日期：2026-11-09）

### 主張 2：狀態碼 ` M` 與未追蹤 `??` 的涵蓋度？

* **主張內容**：` M` 代表已追蹤、已修改、未 staged；未追蹤必為 `??`。是否漏掉其他產線狀態碼？
* **判定**：🟡 **建議修（存在遺漏合法自癒情境）**
* **權威查證**：  
  - ` M` 的官方定義確實為：`X` 為空格（Index 與 HEAD 相同），`Y` 為 `M`（Worktree 被修改且尚未 stage）。
  - **遺漏狀態碼**：
    1. **`M `（已暫存但未提交）**：若先前的腳本在 `git add` 後崩潰，或者 `purge_expired.py` 執行過 `stage_all()`，檔案在 Index 中為 Modified，Worktree 無異動，狀態碼為 `M `。現行程式碼 `$code -ne ' M'` 會將 `M ` 判定為 unsafe。
    2. **`MM`（暫存後又被修改）**：同樣會被視為 unsafe。
    3. **` D`（已追蹤但被工作區刪除）**：在 `purge_expired.py` 刪除資料夾中途逾時時，會大量出現 ` D`，直接導致自癒失效。

  - Git SCM: [git-status - Short Format Table](https://git-scm.com/docs/git-status#_short_format)（查證日期：2026-11-09）

### 主張 5：`NotifyIcon.ShowBalloonTip` 在排程器 Interactive 工作中是否有效？

* **主張內容**：`NotifyIcon.ShowBalloonTip` 能否在排程器工作顯示；Windows 11 與 Session 0 問題。
* **判定**：🔴 **必須修（12 秒強制關閉導致通報失效）**
* **權威查證**：  
  1. **Session 0 隔離**：如果排程設定為「不論使用者登入與否均執行」（S4U / SYSTEM），工作會在 Session 0 執行，**絕對無法**彈出任何 UI 或氣球提示。只有設定為「只在使用者登入時執行」（`-LogonType Interactive`），行程才會跑在互動桌面（Session 1+），此時 WinForms 才能載入桌面 Shell。
  2. **Windows 11 行為**：Windows 10/11 內部已將 `Shell_NotifyIcon` 的氣球提示在底層自動轉譯為 Modern Toast Notification。
  3. **致命漏洞**：程式碼第 58 行呼叫 `Start-Sleep -Seconds 12` 隨後執行 `$ni.Dispose()`。微軟文件與 Win32 API 表明，`Dispose()` 會發送 `NIM_DELETE` 訊息移除通知圖示。通知圖示消失會同步撤銷當前的彈出視窗，且**不會進入 Windows 11 通知控制中心留存**。因此，若排程執行時無人在螢幕前，該通知等同於從未發生。
* **官方來源**：  
  - Microsoft Learn: [NotifyIcon.ShowBalloonTip Method](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.notifyicon.showballoontip)（查證日期：2026-11-09）
  - Microsoft Learn: [Interactive Services / Session 0 Isolation](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)（查證日期：2026-11-09）
  - Microsoft Learn: [Task Security Context](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-security-context)（查證日期：2026-11-09）

### 主張 8：退出碼語意是否與既有系統衝突？

* **主張內容**：0 成功／1 護欄／2 失敗／3 工作區不乾淨／4 假成功／5 等不到腳本。
* **判定**：🟡 **建議修（Exit Code 5 與微軟標準衝突）**
* **權威查證**：  
  在 Windows Win32 API 定義中：
  - `0x0`: `ERROR_SUCCESS`
  - `0x1`: `ERROR_INVALID_FUNCTION`
  - `0x2`: `ERROR_FILE_NOT_FOUND`
  - `0x3`: `ERROR_PATH_NOT_FOUND`
  - `0x5`: `ERROR_ACCESS_DENIED`（存取被拒）
  
  Windows 工作排程器的「上次執行結果（Last Run Result）」欄位在行程退出時，會將 Exit Code 直接映射為 Win32 System Error Message。  
  當 `launch_pipeline.ps1` 拋出 `exit 5`（等不到 G: 上的腳本）時，排程器介面與事件檢視器（Event Viewer TaskScheduler ID 201）會顯示：**`操作已完成，傳回碼: (0x5) / Access is denied`**。維運者會誤以為是執行帳號密碼過期、ACL 權限不足，造成極嚴重的除錯誤導。
* **官方來源**：  
  - Microsoft Learn: [System Error Codes (0-499) - ERROR_ACCESS_DENIED (5)](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)（查證日期：2026-11-09）

### 5.2 修正 `launch_pipeline.ps1`：改善通知留存與調整 Exit Code

1. **更換 Exit Code 5**：改用非系統衝突碼（如 `15` 或 `50`），避免觸發 `0x5 Access is Denied`。
2. **通知常駐與雙保險**：不要使用 `Start-Sleep 12; $ni.Dispose()` 抹殺通知。保留托盤或採用 Windows 原生 PowerShell Toast（寫入 Windows Action Center 留存），並同時在桌面或常用通訊管道發出告警。

```powershell
# 修正退出碼映射，避免 5 (ERROR_ACCESS_DENIED)
function Finish([int]$code, [string]$note) {
  $txt = "{0}  exit={1}  {2}" -f (Get-Date -Format 'yyyy-MM-dd HH:mm:ss'), $code, $note
  [IO.File]::WriteAllText((Join-Path $LOCAL 'LAST-RESULT.txt'), $txt, (New-Object Text.UTF8Encoding $false))
  if ($code -ne 0) {
    $why = switch ($code) {
      1  { '護欄觸發（筆數異常）' }
      2  { '執行失敗' }
      3  { '工作區不乾淨，需要人處理' }
      4  { '假成功：回報 0 但沒有 log' }
      15 { '等不到 G: 上的腳本（超時）' }  # 改用 15 避開 0x5
      default { "未知退出碼 $code" }
    }
    L "❌ $why"
    Notify '法拍上架產線失敗' "$why`n退出碼 $code`n紀錄：$LLOG"
  }
  exit $code
}
```
