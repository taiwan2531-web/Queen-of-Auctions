## 本次改了什麼

### A. `run_pipeline.ps1` 第 0 步自我修復

工作區不乾淨時，逐筆判斷：

- 狀態碼是 ` M`（已追蹤檔案被修改）**且**路徑符合 `^(104woo\.html|w\d+/index\.html)$` → 視為產線殘留
- 全部符合 → `git add -A` + commit，繼續執行
- 有任何一筆不符 → 照舊 `Die ... 3` 停下來等人

### B. `launch_pipeline.ps1` 失敗通知

退出碼非 0 時，用 `System.Windows.Forms.NotifyIcon` 的 `ShowBalloonTip` 顯示提示，
並把結果寫進 `%LOCALAPPDATA%\QueenOfAuctions\LAST-RESULT.txt`。

## 待驗證的技術主張（逐項查證）

| # | 主張 | 需要確認什麼 |
|---|------|------------|
| 1 | `git status --porcelain` 第 1、2 字元為狀態碼，第 4 字元起為路徑 | 官方格式定義；rename（`R  a -> b`）、含空白或非 ASCII 路徑（會被加引號）時，`Substring(3)` 是否仍正確 |
| 2 | ` M` 代表「已追蹤、已修改、未 staged」，未追蹤必為 `??` | 是否存在其他會出現在產線情境的狀態碼（`MM`、`AM`、`UU` 等） |
| 3 | 自動收拾後用 `git add -A` 安全 | **此處是否矛盾**：判斷只看白名單內的檔案，但 `git add -A` 會加入整個工作區。若判斷與 add 之間有新檔案出現（Drive 延遲正是會這樣），會不會把不該收的東西一起 commit |
| 4 | 未追蹤的 `?? wNNN/` 不自動收拾是對的 | 2026-09-20 曾有中斷的上架留下 35 個孤兒資料夾。確認此判斷涵蓋該情境 |
| 5 | `NotifyIcon.ShowBalloonTip` 在工作排程器的 `-LogonType Interactive` 工作中會顯示 | Microsoft 官方說明；Windows 11 是否已改用 toast 而忽略 balloon；工作排程器啟動的程序是否在使用者互動桌面 session |
| 6 | `purge_expired.py` 的「等到核對通過為止、最多 60 秒」能防住 Drive 延遲 | 以時間為界的重試在延遲無上限時是否仍可能漏。**此機制至今未被實戰驗證** |
| 7 | 放在 `%LOCALAPPDATA%` 的腳本工作排程器執行不了 | 2026-09-19 實測：腳本在 AppData 回 `0x8007010B` 或 `0xFFFD0000`，搬到 `C:\Users\ken\Scripts` 後正常。確認成因（當時 Defender 服務未執行、AppLocker 無規則） |
